## 1. R1 공통 전제

issue #72 에 정리된 값 가운데 R1-V02 에 필요한 것만 옮긴다. 출처 문서(통합 표준안, PoC
가이드)는 저장소 밖에 있다.

| 항목 | 값 |
| --- | --- |
| `gate_type` | `feasibility` |
| `ambiguity_required` | `true` — 초기 telemetry 중첩 필수 |
| `expected_overlap` | `powershell_execution`, `remote_session` |
| `expected_divergence` | `credential_access`, `lateral_movement`, `abnormal_process_lineage` |
| `entity_id` | Endpoint Host. Evidence 는 Source Event 가 관측된 host 에 귀속 (D-01, `data-contract-v0.2.md` §5-4) |
| host 구성 | Controller → Target-A. 필요하면 내부 연결 대상 Target-B |
| 네트워크 | Internal / Host-only. **인터넷 연결 없음** |

**S0 의 외부 연결 승인과 무관하다.** S0 는 issue #71 에서 제한된 NAT 예외(방식 A)를 다루지만,
R1-V02 는 내부망 안에서만 동작하므로 그 승인값을 쓰지 않는다.

### 하지 않는 것

```text
현재 단계에서 R1-V02 결과로 탐지 성능을 주장하지 않는다
성능 수치(탐지율, TTSD, FPR 등)를 이 문서에 적지 않는다
계보 Evidence 가 정의되기 전에는 Evidence·Score 경로를 검증 대상으로 삼지 않는다
```

**현재 단계에서 할 수 있는 것은 §8-2 의 telemetry Pilot 까지다** — 원본 Sysmon JSONL 로 연결과
계보를 검증한다. 같은 검증을 정규화 경로로 재현하는 §8-3 Full 은 ProcessGuid 계약이 확장되기
전까지 `blocked` 이다. Pilot 통과는 Full 성공이나 탐지 성능 검증이 아니다. 이유는 §8 과 §10 에 있다.

## 2. R1-V02 원격 프로세스 계보 — 목적과 범위

| 항목 | 값 |
| --- | --- |
| `scenario_id` | `R1` |
| `variation_id` | `V02` |
| 분기 축 | `abnormal_process_lineage` |
| 관측 host | **Target-A 하나** |
| 필요한 Sysmon EventID | 1, 3 |
| 추가 로그 채널 | 없음 |
| 규모 | Normal 1회 + Attack 1회 (R1 Pilot 수집 단계) |

**검증 목적** — 새 로그 채널 없이 **프로세스 계보만으로** Normal 과 Attack 이 갈리는지
확인한다. 두 Run 은 같은 원격 세션과 같은 최종 관리 도구를 쓰고, 그 도구가 원격 세션 host
프로세스의 직접 자식인지(Normal), 중간 프로세스를 거쳤는지(Attack)만 다르다.

**이 Pair 를 먼저 다루는 이유**

- 현재 Sysmon 설정(`configs/sysmon/sysmonconfig-sample-v0.1.xml`)이 기록하는 EID 1·3 만 쓴다
- 현재 normalizer 가 처리하는 `process_create` · `network_connection` 만 쓴다
- 관측 host 가 하나라 `RunMetadata.target_host` 단일값과 맞고, 다중 host 축약 규칙이 필요 없다

## 3. Target-A 기준 관측 구조

```text
Controller                         Target-A (관측 host)                          Target-B
    |                                   |                                           |
    |--- t+0 원격 세션 수립 (WinRM) --->| 원격 세션 host 프로세스 생성               |
    |                                   | t+2 공통 준비 (두 Run 동일)                |
    |                                   | t+5 Normal : host -> 최종 관리 도구        |
    |                                   | t+5 Attack : host -> 중간 -> 최종 관리 도구 |
    |                                   |     (최종 관리 도구 Image 는 두 Run 동일)   |
    |                                   |--- t+8 t+5 관리 도구 인스턴스가 연결 ----->|
```

- Evidence 는 Target-A 의 Source Event 에만 귀속한다
- Controller 와 Target-B 에서 telemetry 를 수집하더라도 **별도 entity** 로 다루고 Target-A 와 합치지 않는다
- 원격 세션 host 프로세스 이름은 `wsmprovhost.exe` 로 **가정**하며, 실제 이름은 rehearsal telemetry 로 확인한다
- WinRM 목적 포트는 `TBD` (§11)

## 4. 행위 목록

`t+분` 은 설계상 상대 시간이다. 실제 기록은 `execution_record` 의 실행 시각이 정본이다.

### 4-1. 공통 구간과 최초 분기

| 시각 | Normal | Attack | 성격 |
| --- | --- | --- | --- |
| t+0 | Controller → Target-A 원격 세션 수립 | 동일 | **공통 준비** |
| t+2 | 원격 세션에서 결과 저장 위치 준비와 로컬 파일 기록 (부수 행위) | 동일 | **공통 준비** |
| t+5 | 원격 세션 host 가 **최종 관리 도구를 직접 실행** — ProcessCreate (계보 깊이 2) | 원격 세션 host → **승인된 중간 프로세스** → **같은 최종 관리 도구** 실행 — ProcessCreate (깊이 3 이상) | **최초 분기** |
| t+8 | t+5 에 생성된 최종 관리 도구 인스턴스가 승인 목적지로 내부 연결 | 동일 (t+5 인스턴스가 같은 목적지 · 포트로 연결) | 분기(연결 주체의 계보) |
| t+10 | 세션 종료 | 세션 종료 | 공통 |

**t+0 ~ t+5 직전은 공통 준비 구간이다.** 두 Run 은 같은 원격 세션에서 같은 준비 작업을 한다.
t+2 의 파일 기록은 부수 행위이며 분기로 쓰지 않는다.

**최초 분기는 t+5 이고, 두 Run 모두 t+5 에 ProcessCreate 가 발생한다.** 최종 관리 도구의
Image 는 두 Run 에서 같다. 다른 것은 **그 최종 프로세스 인스턴스의 부모 계보뿐이다.**

**Normal 도 t+8 에 내부 연결을 만든다.** 두 Run 의 연결은 같은 Image, 같은 목적지, 같은 포트다.
차이는 연결을 만든 인스턴스의 ProcessGuid 와 그 부모 계보에 있다. 연결 유무나 Image 가 답이
되면 hard negative 가 성립하지 않는다.

관리 도구와 중간 프로세스는 **무해한 승인 도구**로 한정하며 구체 선정은 `TBD` 다. 이 문서는
명령·도구 이름·페이로드를 적지 않는다.

### 4-2. reference action

최초 공통 행위(t+0 원격 세션 수립)를 기준으로 하는 것을 제안한다. `reference_time` 은 그
행위가 Target-A 에 남긴 최초 telemetry 시각이다. 확정은 `TBD` (§11).

## 5. 예상 telemetry

### 5-1. Sysmon EventID

| host | EventID | 기대 내용 | 현재 Sysmon 설정으로 나오는가 |
| --- | --- | --- | --- |
| Target-A | **1** ProcessCreate | t+5 두 Run 모두 최종 관리 도구 생성. **Image 동일**, 부모만 다름(Normal: 원격 세션 host, Attack: 중간 프로세스). Attack 에는 중간 프로세스의 EID 1 이 하나 더 있다 | 예 |
| Target-A | **3** NetworkConnect | t+8 두 Run 모두 t+5 최종 관리 도구 인스턴스가 연결. **Image · 목적지 · 포트 동일**, 연결 인스턴스의 **ProcessGuid 와 그 부모 계보가 다름** | 예 |

추가 Sysmon 설정 변경은 필요 없다.

### 5-2. 현재 계약으로 확인할 수 있는 것 — `parent_name`

`normalize_sysmon_process_create` 는 EID 1 의 `ParentImage` 를 `process.parent_name` 으로
옮긴다(`src/incident_awareness/normalization/sysmon.py`). 따라서 **t+5 에서 최종 관리 도구의
직접 부모가 원격 세션 host 인지 여부는 현재 event_v0 로 판정할 수 있다.**

```text
Normal   t+5 최종 관리 도구  process.name = <관리 도구>  process.parent_name = <원격 세션 host>
Attack   t+5 최종 관리 도구  process.name = <관리 도구>  process.parent_name = <중간 프로세스>
```

`process.name` 은 두 Run 에서 같다. 갈리는 것은 `parent_name` 뿐이다.

### 5-3. 현재 계약으로 확인할 수 없는 것 — 계보 깊이와 EID 1 → 3 연결

`ProcessInfo`(`src/incident_awareness/common/models/event.py`)는 `pid`, `name`, `path`,
`command_line`, `parent_pid`, `parent_name` 만 갖고 `extra="forbid"` 다. ProcessGuid 계열
필드가 없다.

| 확인하려는 것 | 필요한 연결 | 현재 |
| --- | --- | --- |
| 계보 깊이 3 이상 | 조부모 이상의 체인 | **불가** — 한 단계 부모 이름만 표현된다 |
| t+8 연결을 만든 프로세스의 계보 | EID 3 과 EID 1 의 결합 | **불가** — 아래 참조 |

Sysmon EID 3 원천에는 `ParentImage` 가 없다(`samples/raw/sysmon-0001.jsonl` 로 확인). 그래서
정규화된 `network_connection` 의 `process.parent_name` 은 항상 `null` 이다. 연결 주체의 계보를
알려면 EID 3 의 `ProcessGuid` 로 EID 1 을 찾아야 하는데, 그 값이 event_v0 에 남지 않는다.
`parent_pid` 로 잇는 방법은 PID 가 재사용될 수 있어 신뢰하지 않는다.

**결과적으로 정규화 경로(event_v0)에서 가능한 R1-V02 는 "한 단계 부모 이름" 으로만 갈리는 약한
형태다.** §7 의 변형처럼 Normal 에도 승인 wrapper 를 넣으면 한 단계 부모만으로는 구분이 사라진다.

이 제한은 정규화 경로에만 해당한다. 원본 Sysmon JSONL 에는 `ProcessGuid` · `ParentProcessGuid` 가
남아 있으므로, 원본을 쓰는 §8-2 Pilot 은 EID 1 ↔ EID 3 연결과 전체 계보를 검증할 수 있다.

## 6. Ground Truth

`data-contract-v0.2.md` 의 RunMetadata · ExecutionRecord 경계를 따른다. R1-V02 에서 추가로
남길 항목은 다음과 같다.

| 항목 | 기록 위치 |
| --- | --- |
| `scenario_id` · `variation_id` · `run_id` · `run_type` · 반복 번호 | RunMetadata |
| 행위별 실행 시각 | `execution_record.csv` |
| reference action 과 `reference_time` · `reference_source_event_id` | RunMetadata |
| 최초 분기 action | 이 문서의 행위 표 |
| 단계별 프로세스 이름 · 경로 · ProcessGuid · ParentProcessGuid | 실행 기록(원천 telemetry 에서 추출) |
| t+5 최종 관리 도구 인스턴스의 ProcessGuid 와 Image | 실행 기록 |
| 계보 깊이 (Normal 2 / Attack 3 이상) | 실행 기록 |
| t+8 연결의 ProcessGuid · 목적지 IP · 포트 · 시각 · host | 실행 기록 |
| 승인된 목적지 IP · 포트와 t+5 · t+8 판정 시간 구간 | 이 문서 §11 (`TBD`) |
| Sysmon config version · hash | RunMetadata · Manifest |
| snapshot 이름과 복원 확인 | RunMetadata(`vm_snapshot`) · 실행 기록 |

`ExecutionRecordRow` 에는 host 필드가 없다(issue #72 질문 7). R1-V02 는 관측 host 가
Target-A 하나이므로 행위 표와 `action_id` 로 충분하다고 보고 ExecutionRecord 계약을 바꾸지 않는다.

ProcessGuid 는 event_v0 에 들어오지 않으므로 **원천 telemetry 에서 뽑아 실행 기록으로만**
보관한다. Ground Truth 는 런타임 입력이 아니므로 이 값이 Evidence 나 Fusion 에 흘러가지 않는다.

## 7. hard negative 와 변형 축

**Normal 은 idle 이 아니다.** 같은 원격 세션을 열고, t+5 에 같은 최종 관리 도구를 실행하고,
t+8 에 같은 목적지 · 포트로 내부 연결까지 만든다. Attack 과 다른 것은 최종 관리 도구 인스턴스의
부모 계보뿐이다.

| 축 | 변형 | 비고 |
| --- | --- | --- |
| 계보 깊이 | 3단계 / 4단계 | 깊이 자체가 정답이 되지 않도록 Normal 에도 승인 wrapper 변형 검토 |
| 중간 프로세스 종류 | 스크립트 해석기 / 승인 wrapper | 구체 선정 `TBD` |
| 분기 시각 | t+5 / t+9 | Fusion window 보다 충분히 넓게 |
| 연결 대상 | Target-B / 내부 파일 서버 | 실험망 CIDR 필수(`TBD`) |

**Shortcut 통제** — 프로세스·파일 이름에 `attack_`·`normal_` 같은 prefix 를 두지 않는다. 계정,
작업 디렉터리, 행위 수는 두 Run 에서 같게 한다.

## 8. 성공 · 실패 판정

**이 판정은 telemetry 수집 품질에 대한 것이다.** 탐지 성능 판정이 아니다.

**t+8 에 EID 3 이 있다는 사실만으로는 어느 단계에서도 통과로 보지 않는다.** 두 Run 모두 같은
Image 로 같은 목적지에 연결하므로, EID 3 의 존재는 Normal 과 Attack 을 구분하지 못한다.

### 8-1. 검증 조건

두 Run 각각에 대해 아래를 **모두** 만족해야 한다. 이 조건은 §8-2 Pilot 과 §8-3 Full 에 똑같이
적용되며, 두 단계는 **어떤 데이터 경로로 확인하느냐**만 다르다.

| # | 조건 |
| --- | --- |
| S-1 | 공통 준비 구간(t+0 ~ t+5 직전)에서 두 Run 의 관측 EventID 종류와 프로세스 계보가 같다 |
| S-2 | t+5 판정 구간에 **지정 최종 관리 도구의 EID 1** 이 있고, 두 Run 의 Image 가 같다. 이 EID 1 의 ProcessGuid 를 기준값으로 삼는다 |
| S-3 | 그 EID 1 의 부모 계보가 Run 유형과 맞다 — Normal 은 원격 세션 host 가 직접 부모, Attack 은 승인된 중간 프로세스가 부모이고 그 부모가 원격 세션 host |
| S-4 | **S-2 의 ProcessGuid 와 같은 ProcessGuid 를 가진 EID 3** 이 있다 |
| S-5 | 그 EID 3 의 목적지 IP 가 승인된 값이다 (`TBD`, §11) |
| S-6 | 그 EID 3 의 목적지 포트가 승인된 값이다 (`TBD`, §11) |
| S-7 | 그 EID 3 의 시각이 지정된 t+8 판정 구간 안이다 (`TBD`, §11) |
| S-8 | S-2 의 EID 1 과 S-4 의 EID 3 이 모두 예상 host(Target-A)에서 기록됐다 |

판정 단계와 현재 상태는 다음과 같다.

| 단계 | 데이터 경로 | 현재 상태 | 결과 표기 |
| --- | --- | --- | --- |
| **telemetry Pilot** (§8-2) | Target-A 원본 Sysmon JSONL | 실행 가능 | `pass` / `fail` |
| **Full** (§8-3) | NormalizedEvent → Evidence → Fusion · 평가 입력 | **`blocked`** | `not_evaluated` |

### 8-2. telemetry Pilot — 원본 JSONL 로 연결 · 계보 검증

원본 Sysmon JSONL 은 ProcessGuid 를 그대로 갖고 있다. 그래서 Pilot 은 필드가 있는지만 보지 않고
**실제 연결이 일치하는지까지** 원본 레코드로 검증한다.

**확인 절차**

1. t+5 판정 구간에서 지정 최종 관리 도구의 EID 1 을 찾고 그 `ProcessGuid` 를 기준값으로 삼는다
2. t+8 판정 구간에서 **그 ProcessGuid 와 같은 `ProcessGuid` 를 가진 EID 3** 을 찾는다
3. 그 EID 3 의 `DestinationIp` · `DestinationPort` · 시각 · `Computer` 를 승인값과 비교한다
4. 두 Run 의 t+5 최종 관리 도구 `Image` 를 비교한다
5. 원본 EID 1 의 `ParentProcessGuid` 를 따라 올라가 두 Run 의 부모 계보를 비교한다

**Pilot 통과** — 두 Run 모두 §8-1 의 S-1 ~ S-8 을 원본 JSONL 에서 만족한다. 즉 아래가 모두 참이다.

| 확인 | 대응 조건 |
| --- | --- |
| t+5 지정 최종 관리 도구의 EID 1 이 있고 그 `ProcessGuid` 가 있다 | S-2 |
| Normal 과 Attack 의 최종 `Image` 가 같다 | S-2 |
| 두 Run 의 부모 계보 차이가 원본 EID 1 체인에서 확인된다 | S-3 |
| t+8 판정 구간에 EID 3 이 있고 그 `ProcessGuid` 가 t+5 EID 1 과 같다 | S-4 |
| 목적지 IP · 포트가 승인값과 같다 | S-5 · S-6 |
| 시각이 허용된 t+8 구간 안이다 | S-7 |
| EID 1 과 EID 3 이 모두 Target-A 에서 기록됐다 | S-8 |
| 공통 준비 구간의 EventID 종류와 계보가 두 Run 에서 같다 | S-1 |

**Pilot 실패** — 아래 중 하나라도 해당하면 실패다.

- t+5 지정 최종 관리 도구의 EID 1 이 없거나 `ProcessGuid` 가 없다
- 두 Run 의 최종 `Image` 가 다르다
- 부모 계보 체인이 중간에 끊겼거나, Normal 과 Attack 의 계보가 같다
- t+8 구간의 EID 3 이 **다른 프로세스의 것**이다 — `ProcessGuid` 가 t+5 EID 1 과 다르다
- EID 3 의 목적지 IP · 포트 · 시각 · host 중 하나라도 승인값과 다르다
- 공통 준비 구간의 EventID 종류나 계보가 두 Run 에서 다르다

**Pilot 통과는 Full 성공이 아니며 탐지 성능 검증도 아니다.** 원본 telemetry 에 판정 근거가 실제로
남는다는 것만 확인한다. 이 결과로 R1-V02 의 성공이나 성능을 보고하지 않는다.

### 8-3. Full — 정규화 경로로 같은 검증을 재현

Full 은 §8-2 와 **같은 연결 · 계보 검증을** 원본 JSONL 이 아니라 파이프라인 경로로 재현하는 단계다.

```text
NormalizedEvent  ->  Evidence  ->  Fusion · 평가 입력
```

**현재 상태는 `blocked` 이고 결과는 `not_evaluated` 로 표기한다.** event_v0 에 ProcessGuid 가 없어
(§5-3) S-4 의 EID 1 ↔ EID 3 결합과 S-3 의 전체 계보를 정규화 경로에서 재현할 수 없다. 계보
분기를 나타낼 `evidence_type` 도 아직 없다(§10).

| 구분 | 기준 |
| --- | --- |
| 해제 조건 | ProcessGuid 이벤트 계약 확장, 계보 `evidence_type` 정의 (§10) |
| 통과 | 정규화 경로에서 S-1 ~ S-8 을 재현하고, 그 결과가 같은 Run 의 Pilot 결과와 일치한다 |
| 실패 | 정규화 경로에서 S-1 ~ S-8 중 하나라도 재현되지 않거나, Pilot 결과와 다르다 |

### 8-4. 무효

두 단계 모두 아래에 해당하면 판정하지 않는다.

| 기준 |
| --- |
| snapshot 미복원 상태 실행 |
| 같은 `run_id` 재사용 |
| 승인되지 않은 도구 사용 |

## 9. 안전 조건

- 격리된 Controller · Target VM 과 복원 가능한 snapshot 에서만 실행한다
- Internal / Host-only 네트워크만 쓴다. 공인 인터넷 연결은 없다
- 실제 운영 계정 · 운영 호스트를 쓰지 않는다
- 관리 도구와 중간 프로세스는 무해한 승인 도구로 한정한다
- 자격증명 접근 · 덤프 · 로그 삭제 · 권한 변경은 이 Pair 에 포함하지 않는다
- 추가 승인은 필요 없다. 다만 도구 선정(`TBD`)은 실행 전에 확정한다

## 10. 구현 의존성

| 의존 | 내용 | 확인 대상 |
| --- | --- | --- |
| 계보 Evidence | 계보 분기를 나타낼 `evidence_type` 이 없다. `configs/evidence_types_v0.2.yaml` 은 S0 용 2종뿐 | 역할 2 — issue #85 |
| ProcessGuid 계약 확장 | 깊이 3 이상과 EID 1 → 3 연결에 필요. `ProcessInfo` 에 필드를 추가하면 `data-contract-v0.2.md` §2 에 따라 NormalizedEvent 버전을 올려야 한다 | **이벤트 계약 담당** |
| 내부 연결 Evidence | `script_interpreter_external_connection` 은 전역 IP 만 인정해 내부 연결은 Evidence 가 되지 않는다 | 역할 2 |
| R1 Fusion profile | `configs/fusion/fusion_config_v0.1.yaml` 은 `s0-profile` 과 S0 Evidence 만 포함 | 역할 5 |
| 원격 실행 runner | 현재 S0 runner 는 로컬 실행만 한다. 원격 세션 수립과 Target-A 수집이 새로 필요 | 역할 4 — issue #73 |
| S0 runner 병합 | R1 runner 는 S0 의 공통 함수를 재사용할 예정이라 PR #94 병합 뒤 착수 | 역할 4 |

**이 의존성 때문에 현재 단계에서는 §8-2 의 telemetry Pilot 까지만 가능하다.** Pilot 은 원본
JSONL 로 연결 · 계보를 검증하지만, 같은 검증을 정규화 경로로 재현하는 §8-3 Full 은 ProcessGuid
계약과 계보 Evidence 가 정해지기 전까지 `blocked` 이다. 그 전에는 Evidence · Score · Stopping
경로를 R1-V02 로 검증하지 않는다.
