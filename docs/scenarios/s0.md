## 1. 목적

S0 는 **파이프라인 검증 게이트**다. 아래 경로가 끝까지 도는지 한 번 확인하는 것이 유일한
목적이다.

```text
VM -> Sysmon -> Raw Export -> 정규화 -> Evidence -> Score -> Stopping -> evaluation_v0
```

| 항목 | 값 |
| --- | --- |
| `scenario_id` | `S0` |
| `family_id` | `local_powershell` |
| `variation_id` | `v1` |
| `gate_type` | `pipeline_validation` |
| `ambiguity_required` | `false` |
| `performance_claim_allowed` | **`false`** |
| `decisive_comparator.required` | `false` |
| `parallel_required` | `false` (Fast Path 선택적) |
| 규모 | Normal 1회 + Attack 1회 |

### 하지 않는 것

```text
S0 결과로 핵심 가설을 판정하지 않는다
S0 결과를 성능 비교·주장에 사용하지 않는다
S0 에서 Fast 시나리오를 늘리지 않는다
```

**S0 에서 정상/공격 궤적이 분리되지 않는 것은 정상적인 결과이며 가설의 반증이 아니다.**
PASS/FAIL 은 참고 기록이고 원인 점검 절차를 발동시키지 않는다. 핵심 가설의 실질 판정은
R1 에서 처음 이루어진다.

## 2. Pair 설계

Pair 설계에서 중요한 것은 공격 명령 자체가 아니라 세 가지다.

### 2-1. 왜 Pair 로 묶었는가

"PowerShell 이 외부와 통신한다"는 사실만으로는 정상과 공격을 가를 수 없다. 관리자가 모듈을
받거나 외부 API 를 조회하는 것은 일상적인 업무다. 따라서 **두 Run 모두 PowerShell 을 실행하고
외부로 연결한다.** 차이는 통신 여부가 아니라 실행 방식에 있다.

### 2-2. 어느 부분이 겹치는가

```text
powershell_execution        정상·공격 모두 PowerShell 을 실행한다
external_connection         정상·공격 모두 외부 IP 로 TCP 연결한다
local_file_activity         정상·공격 모두 로컬 파일을 다룬다
```

### 2-3. 어디서 갈릴 것으로 예상하는가

```text
obfuscated_invocation       공격만 -EncodedCommand 로 실행한다
```

S0 는 `ambiguity_required: false` 이므로 이 정도의 중첩을 요구하지 않는다. 그러나 정상 Run 을
idle 로 두면 아래 §6 의 문제가 생기므로, 최소한의 겹침은 의도적으로 넣는다.

## 3. Evidence 조건과의 대응

`configs/evidence_types_v0.2.yaml` 의 두 유형이 S0 telemetry 에서 실제로 성립해야 한다.
조건은 역할 2가 확정한 값이다.

| `evidence_type` | 조건 |
| --- | --- |
| `encoded_powershell_command` | `event_type = process_create` / image 가 powershell·pwsh / command line 에 `-enc` 또는 `-encodedcommand` |
| `script_interpreter_external_connection` | `event_type = network_connection` / **연결을 발생시킨 프로세스 자체**가 powershell·pwsh·cmd·wscript·cscript / `dst_ip` 가 외부(Global) IP |

두 번째 조건은 **부모 프로세스가 아니라 연결 주체**를 본다. 그리고 loopback·사설 IP 로는
성립하지 않는다.

### Run 별 성립 여부

| `evidence_type` | Normal | Attack |
| --- | :---: | :---: |
| `encoded_powershell_command` | ✕ | ○ |
| `script_interpreter_external_connection` | ○ | ○ |

> 두 유형은 First Cycle 의 `Event -> Evidence -> Fusion` 흐름을 검증하기 위한 대표값이며 최종
> 목록이 아니다. 파일 수집·로그 삭제 같은 행위를 Evidence 로 올릴지는 이 시나리오가 확정된
> 뒤 역할 2와 역할 4가 함께 정한다.

## 4. 행위 목록

시각은 설계값이다. **실제 기록은 `execution_record` 의 절대 시각이 정본**이며, 아래
`offset_min` 을 그대로 옮기지 않는다.

### 4-1. Normal Run (`run_type = normal`)

| `action_id` | `offset_min` | `action_type` | 행위 | 기대 telemetry |
| --- | ---: | --- | --- | --- |
| `N01` | 0 | `admin_action` | 관리 스크립트 실행 (평문 PowerShell) | Sysmon EID 1 |
| `N02` | 2 | `admin_action` | PowerShell 로 외부 HTTPS 조회 | Sysmon EID 3 (dst = Global IP) |
| `N03` | 5 | `file_operation` | 업무 파일 복사·압축 | Sysmon EID 1 |
| `N04` | 8 | `admin_action` | 로컬 백업·정리 작업 | Sysmon EID 1 |

### 4-2. Attack Run (`run_type = attack`)

| `action_id` | `offset_min` | `action_type` | 행위 | 기대 telemetry |
| --- | ---: | --- | --- | --- |
| `A01` | 0 | `execution` | **난독화 PowerShell 실행 (`-EncodedCommand`)** | Sysmon EID 1 |
| `A02` | 2 | `command_and_control` | 해당 PowerShell 이 외부로 TCP 연결 | Sysmon EID 3 (dst = Global IP) |
| `A03` | 5 | `collection` | 로컬 디렉터리 수집·압축 | Sysmon EID 1 |
| `A04` | 8 | `execution` | 후속 프로세스 실행 | Sysmon EID 1 |

`A02` 는 `A01` 이 만든 프로세스가 직접 연결해야 한다. 별도 프로세스가 연결하면
`script_interpreter_external_connection` 의 프로세스 조건을 만족하더라도 `A01` 과의 인과가
끊긴다.

**구현 주의** — `-EncodedCommand` 로 인코딩하는 명령 자체에 연결 코드를 넣어야 한다.
난독화 PowerShell 을 띄운 뒤 다른 프로세스에서 연결하면 조건은 충족되지만 인과가 없다.
확인은 Sysmon `ProcessGuid` 로 한다.

```text
EID 1 (A01) 의 ProcessGuid  ==  EID 3 (A02) 의 ProcessGuid      o
EID 1 (A01) 의 ProcessGuid  !=  EID 3 (A02) 의 ProcessGuid      x  인과 없음
```

`samples/raw/` 의 스키마 샘플은 이 조건을 만족하지 않는다. 그 샘플에서 외부 연결을 낸 것은
수집 스크립트 자신이며, 난독화 PowerShell 의 자식도 아니다. 두 Evidence 조건이 각각
성립한다는 것만 보여 줄 뿐 인과를 보여 주지 않는다.

### 4-3. 범위 밖

```text
PowerShell Operational (4104)
Windows Security (4624 / 4688 / 1102)
원격 세션 / Controller VM
```

`configs/event_types_v0.2.yaml` 에는 `script_block`·`file_create`·`registry_change` 가 있으나
`docs/schema/event-v0.md` §6 이 초기 검증 대상을 `process_create` 와 `network_connection`
두 가지로 한정한다. 로그 삭제(1102)와 원격 접근(5140 / 4624 Type 3)은 **R1 승격 시** 다룬다.

## 5. Run 식별과 메타데이터

`run_id` 는 불투명 식별자이며 정상·공격·시나리오 의미를 문자열에 포함하지 않는다.
소비자는 `run_id` 에서 `run_type` 이나 `scenario_id` 를 파싱하지 않는다.

```text
run_id      RUN-YYYYMMDD-NNN
scenario_id S0
run_type    normal | attack
```

`RunMetadata` 는 `docs/schema/run-id.md` 를 따른다. S0 에서 채우는 값은 다음과 같다.

| 필드 | Normal | Attack |
| --- | --- | --- |
| `scenario_id` | `S0` | `S0` |
| `run_type` | `normal` | `attack` |
| `family_id` | `local_powershell` | `local_powershell` |
| `variation_id` | `v1` | `v1` |
| `repetition` | 반복 실행 번호 | 반복 실행 번호 |
| `target_host` | `WIN-01` | `WIN-01` |
| `start_time` / `end_time` | 실행 실측 UTC | 실행 실측 UTC |
| `reference_time` | **`null`** | 아래 §6 |
| `reference_action_id` | **`null`** | `A01` |
| `reference_source_event_id` | **`null`** | 아래 §6 |
| `reference_policy_version` | `ref-v0.1` | `ref-v0.1` |
| `detector_set_version` | 아래 §5-1 | 아래 §5-1 |
| `sysmon_config_version` | 동일 값 | 동일 값 |
| `vm_snapshot` | 동일 값 | 동일 값 |
| `scenario_version` | `v1` | `v1` |
| `schema_versions` | 아래 §5-1 | 아래 §5-1 |

`RunMetadata` 는 정상 Run 의 `reference_time` 이 `null` 이 아니면 검증 오류를 낸다.

> **`reference_policy_version` 의 필수 여부가 두 문서에서 갈린다.**
>
> ```text
> docs/schema/run-id.md            필수 O / null X
> docs/data-contract-v0.2.md §4    필수 X / null O
> src/.../models/run.py            str | None = None  -> 선택
> ```
>
> `run-id.md` 는 스스로 상위 정본을 `data-contract-v0.2.md` 로 선언하고 있고 코드도
> 그쪽을 따르므로 `run-id.md` 표가 낡은 것으로 보인다. S0 는 두 Run 모두 값을 채우므로
> 실행에는 영향이 없으나, 문서 소유자인 역할 3의 확인이 필요하다(§11 남은 항목 7).

### 5-1. 필수 필드 보충

`docs/data-contract-v0.2.md` §4 가 필수(null 불가)로 지정한 필드 중 값이 자명하지 않은
것을 정리한다.

**`target_host`** — S0 는 VM 한 대이므로 두 Run 이 같은 값을 쓴다. 실험 VM 의 컴퓨터명을
`WIN-01` 로 맞추면 `docs/schema/event-v0.md` 의 `host_id` 예시와도 일치한다.

**`schema_versions`** — 9 개 키를 모두 포함해야 하며 각 값은 비어 있지 않은 문자열이어야
한다. `docs/data-contract-v0.2.md` §2 버전표를 적용하면 S0 에서는 다음과 같다.

```yaml
schema_versions:
  run_metadata:     v0.2
  event:            v0.2
  evidence:         v0.2
  fast_hit:         v0.2
  detection_result: v0.2
  fusion_result:    v0.2
  decision_result:  v0.2
  execution_record: v0.1
  evaluation_input: v0.1
```

**`detector_set_version`** — S0 는 Fast Path 를 쓰지 않으므로 동결된 detector set 이 없다.
표기 방식이 두 문서에서 갈리므로 §11 남은 항목 6 으로 둔다.

```text
PoC 착수 가이드 v1.1 §2-1   detector 를 안 쓰면 none
data-contract v0.2 §4       필수 아님, null 허용 (Pydantic 도 str | None)
```

문자열 `none` 은 매직 값이라 `null` 이 더 적절해 보이나 RunMetadata 소유자인 역할 3이 정한다.

### Ground Truth 경계

```text
Ground Truth  ->  evaluation      ○
Ground Truth  ->  Evidence / Fusion / Fast runtime   ✕
```

Normalizer·Evidence·Fusion·Fast runner 의 런타임 경로는 `run_type` 과 `reference_time` 을
읽지 않는다. Ground Truth 는 Raw telemetry 와 별도 경로에 보관하고 역할 5의 평가 단계에서만
런타임 결과와 결합한다.

`execution_record` 는 **정상 Run 에도 작성한다.** 정상 Run 에서 오경보가 났을 때 어떤 정상
행위 때문인지 역추적하려면 필요하다.

## 6. reference_time

detector 결과가 아니라 **orchestration 실행기록과 raw telemetry 의 정렬**로 정한다.

```text
A01 실행 시각                                    execution_record 에 기록
      |
      +--> A01 에서 파생된 최초 observable telemetry   <- reference_time
      |
      +--> (무관) 이후 detector 가 무엇을 언제 잡았는지
```

최초 탐지를 기준으로 삼으면 detector 가 자기 출발선을 스스로 정하는 순환이 생긴다.

S0 에서 `A01` 이 만드는 최초 telemetry 는 난독화 PowerShell 의 `process_create` 다.

### `reference_source_event_id` 는 Sysmon RecordId 를 기록한다

`docs/schema/event-v0.md` §5 는 `source_event_id` 를 Sysmon Record ID 나 GUID 같은
**source-native identity** 로 정의한다. 반면 `docs/data-contract-v0.2.md` §5-2 는 Provenance
체인을 `Evidence.event_ids -> NormalizedEvent.event_id -> raw_ref -> Manifest` 로 규정하고
`source_event_id` 는 Manifest 를 직접 resolve 하는 필드가 아니라고 명시해, 두 후보가 가능했다.

```text
후보 A   Sysmon RecordId           예: "3391"      정규화 전에 확정 가능
후보 B   NormalizedEvent.event_id  예: "evt-001"   정규화(P6) 이후에야 확정
```

**RunMetadata 소유자인 역할 3이 후보 A 로 확인했다**(PR #58 리뷰). 따라서 이 값은
Sysmon 이 부여한 RecordId 를 그대로 기록한다.

작업 순서에 영향이 있다. 후보 B 였다면 `reference_time` 확정이 정규화(P6) 이후로 밀렸겠지만,
후보 A 이므로 **Attack Run 을 실행한 직후(P4)에 확정할 수 있다.** raw telemetry 만 있으면
되기 때문이다.

## 7. Shortcut 통제

정상 Run 이 idle 이고 공격 Run 만 바쁘면 모델은 "악성행위"가 아니라 **"컴퓨터가 바쁜가"** 를
학습한다. 아래 항목이 `run_type` 과 완전 분리되지 않도록 통제한다.

| 항목 | 통제 |
| --- | --- |
| 계정명 | **동일 계정** 사용 |
| 호스트명 | 동일 (S0 는 VM 1대) |
| 실행 경로 | 두 Run 모두 같은 작업 디렉터리에서 실행 |
| 파일명 패턴 | 공통 접두어 사용. `attack_*` / `normal_*` 금지 |
| Run 관측 길이 | 동일하게 맞춘다 |
| Event 개수 | 행위 수를 4건으로 동일하게 맞춘다 |
| 실행 순서·날짜 | 같은 세션에서 교차 실행. 정상만 먼저 몰아서 실행하지 않는다 |
| `vm_snapshot` | 동일 스냅샷에서 복원 |
| `sysmon_config_version` | 동일 값 |

### 통제하지 않는 것 — 의도한 신호

`-EncodedCommand` 는 `run_type` 과 완전 분리되지만 **shortcut 이 아니라 이 시나리오가 검증
하려는 신호 자체**다. Evidence 조건이 그 옵션을 직접 보도록 정의돼 있으므로 제거하면 검증할
대상이 사라진다.

shortcut 과 신호를 구분하는 기준은 "그 차이가 **행위의 의미**인가, 아니면 **라벨의 흔적**인가"
다. 계정명이 다른 것은 라벨의 흔적이고, 난독화 실행은 행위의 의미다.

### PASS/FAIL 기준을 두지 않는다

표본이 적은 초기 단계에서는 분류기 성능 추정의 변동성이 커서 단일 임계값을 게이트로 쓰면
정상 데이터를 잘못 탈락시킨다. 감사 결과는 **기록**하되 통과 조건으로 쓰지 않는다.

## 8. 예상 점수 궤적과 파이프라인 검증 범위

S0 scoring profile 의 `evidence_type` 은 2종이므로 가능한 점수는 `0 / 0.5 / 1.0` 세 값이다.

```text
             N01/A01   N02/A02   N03/A03   N04/A04
Normal        0.0       0.5       0.5       0.0
Attack        0.5       1.0       1.0       0.5
```

위 표는 예시이며 실제 값은 `feature_window_size_sec` 에 따라 달라진다. Evidence 가 window
에서 빠지면 점수는 내려간다. 점수가 내려오지 않는다면 누적형 피처를 쓰고 있다는 뜻이고,
그 경우 임계·지속성 sweep 이 무의미해진다.

정상 Run 에서 `script_interpreter_external_connection` 하나가 성립하므로 **정상 궤적이 0 에
머무르지 않는다.** 이는 성능을 주장하기 위한 설계가 아니라, 평가 파이프라인의 분기를 한 번씩
태우기 위한 것이다.

| `τ_on` | 검증되는 경로 |
| --- | --- |
| `1.0` | 공격만 ACTIVE -> Run Recall 분자, TTSD 계산 경로 |
| `0.5` | 정상도 ACTIVE -> **false-alert episode 집계, FA/BH 분모·분자 경로** |

정상 Run 이 아무 Evidence 도 만들지 않으면 오경보 집계 경로가 한 번도 실행되지 않아
파이프라인의 절반이 검증되지 않는다.

### S0 에서 기대하는 Decision 결과

S0 는 Fast Path 를 쓰지 않으므로 `parallel_required = false` 인 Config 로 실행한다.
따라서 Fast evaluator 가 실행되지 않는다.

```text
fast_status    not_evaluated
fusion_status  detected | miss
```

**`decision_path` 와 `winning_path` 의 값은 이 문서가 정하지 않는다.**
`docs/data-contract-v0.2.md` §8 은 `parallel_required = true` 일 때 한 경로라도
`not_evaluated` 이면 세 값이 모두 `null` 이고 병렬 검증 실패로 처리하도록 규정한다. 그리고
`parallel_required = false` 인 Run 에 대해서는 이렇게 명시한다.

> `not_evaluated` 허용 범위와 Decision 계산 규칙은 해당 실행 Config 에서 별도로 정의한다.

즉 S0 에서 `fast_status = not_evaluated` 를 정상으로 보고 `decision_path` 를 `fusion` 으로
둘지, 아니면 `null` 로 둘지는 **실행 Config 가 소유한다.** 그 Config 와 `config_version` 은
아직 없다(§11 남은 항목 4). Config 가 정해지기 전에는 이 문서가 값을 단정하지 않는다.

3층 병렬 검증은 R1 부터 의미를 가진다.

## 9. 산출물

Run 1회마다 다음을 생성한다.

```text
data/raw/<run_id>/telemetry/       sysmon.evtx, sysmon.jsonl
data/raw/<run_id>/detector/        S0 는 비어 있어도 무방
data/raw/<run_id>/manifest.json    path / sha256 / layer

data/ground_truth/<run_id>/execution_record.csv
data/ground_truth/<run_id>/run_metadata.json
```

`data/` 는 `.gitignore` 대상이다. Git 에는 설정·스키마·코드·시나리오 정의·manifest 만 올린다.

### 반드시 기록할 것 — Pair 제작 시간

```text
T_setup      환경·telemetry 준비 (1회성, 단가에서 제외)
T_scenario   정상·공격 행위 구현
T_collect    실행 및 로그 수집
T_validate   의도한 telemetry 생성 여부 검증
```

이 값이 R1·R2 및 전체 데이터 규모를 결정한다. S0 는 1회성 setup 이 섞여 있으므로 R1 제작
시간을 별도로 측정해야 실제 단가가 나온다.

### 시간 압축

S0 및 개발·디버깅 목적의 압축 실행은 제한하지 않는다. 핵심 성능 주장에 사용하는 R1·R2 는
가급적 비압축으로 수행한다.

## 10. R1 승격 시 달라지는 것

이 시나리오를 그대로 R1 로 올리지 않는다. R1 은 `ambiguity_required: true` 이고 성능 주장이
허용되므로 요구 수준이 다르다.

| 항목 | S0 | R1 |
| --- | --- | --- |
| 게이트 | 파이프라인 검증 | Feasibility |
| 중첩 구간 | 요구하지 않음 | **필수** |
| decisive comparator | 선택 | **R1 실행 전 필수·동결** |
| VM | 1대 | **Controller + Target** |
| 성능 주장 | 금지 | 허용 |
| 추가 telemetry | — | 원격 접근, 로그 삭제 등 |

R1 에서 `NONE` 이 나오면 원인 점검 5단계 중 4개가 역할 4의 책임 영역이다.
